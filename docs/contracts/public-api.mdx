This document records the public surfaces that should remain stable across feature flags and refactors. Treat it as a human-readable companion to `tests/golden/` and `./tools/check.sh`.

## Workspace crates

Public library and binary surfaces live under `crates/`:

- `abi-foundation` — shared utilities, credentials, HTTP helpers, plugin manifest validation
- `abi-core` — config, memory, scheduler, plugin registry
- `abi-ai` — profiles, identity, routing, completion/training helpers
- `abi-wdbx` — vector/key-value/block store, WAL, cluster/compute/secure demos, REST
- `abi-gpu` — GPU capability/status reporting, optional Metal DOT, shaders/mlir/mobile report surfaces
- `abi-connectors` — local/live connector boundaries
- `abi-agent-runtime` / `abi-agent-host` — provider-neutral run contracts and bounded audited tool orchestration
- `abi-models` — signed immutable registry, consent, verified download, and external-storage contracts
- `abi-model-runtime` — explicit Candle local-model loading with separate load/execution evidence
- `abi-plugins` — bundled plugins + `PluginManager` (compile-time `Plugin` trait + mod/stub parity)
- `abi-sea` / `abi-nn` / `abi-telemetry` — feature crates behind the same workspace
- `abi-cli` — binary `abi` (frozen 13-command CLI)
- `abi-mcp` — binary `abi-mcp` (frozen 12 MCP tools)

There is no monolithic root crate re-exporting every namespace; consumers depend on the workspace crates above.

`abi-model-runtime` publishes `LocalModelProvider`, `DevicePreference`, `LoadReport`, and `InferenceReport`. Loading requires the exact model ID, accepting principal, external storage root, and device choice; there is no global model/device default and no silent substitution or fallback. Its first implemented architecture is the generated-test-only `abi-bigram-v1` transition fixture, which proves real Tokenizers, Safetensors, Candle CPU, and locally exercised Metal execution without placing model artifacts in the repository. The `cuda` feature wires Candle's CUDA backend for toolkit-equipped builds, but compilation and runtime execution are not claimed on hosts without `nvcc`. Gemma and structured tool-call generation are not part of this surface yet.

## Feature gates and plugin parity

Feature and plugin surfaces keep real/`stub` public API parity via the Rust type system: both `mod.rs` and `stub.rs` implement the `Plugin` trait in `crates/abi-plugins`, with `assert_plugin_parity!` covering metadata constants. This replaces the former declaration-name parity gate; it is still not a complete behavioral equivalence checker.

Representative feature crates / modules:

- `ai` (`abi-ai`)
- `gpu` / `shaders` / `mlir` / `mobile` (`abi-gpu`)
- `wdbx` (`abi-wdbx`)
- `sea` (`abi-sea`)
- `nn` (`abi-nn`)
- `telemetry` / metrics-style exporters (`abi-telemetry`, plugins)
- connectors / OS-control helpers as wired through CLI and connectors

Disabled features should return stable no-op or explicit disabled-feature responses rather than removing public symbols. Workspace tests under `./tools/check.sh` and golden fixtures under `tests/golden/` guard the frozen CLI/MCP surfaces.

The GPU crate has a stable runtime contract across real and disabled builds: all declared backends are listed, detection returns a safe backend status, and vector work uses linked Metal **DOT** on macOS when the `metal-kernels` feature initializes a device/pipeline (`crates/abi-gpu/src/metal_kernels.rs`); otherwise deterministic CPU SIMD fallback with `accelerated=false`. Status reporting explains whether Metal/native kernels are active or falling back. This does not prove CUDA/Vulkan/ANE dispatch, a broader Metal kernel suite, or GPU speedup figures.

The mobile surface exposes a stable profile contract across real and disabled builds: platform/profile metadata and layout validation helpers report honestly. Real desktop builds use a simulated mobile profile, and disabled builds preserve the same public symbols with explicit disabled responses. This contract does not prove native iOS/Android dispatch.

The WDBX store contract exposes key-value counts, vector counts, block counts, spatial record counts, temporal node/edge counts, vector dimensions, next vector ID, and acceleration status via store `stats()` / manifest export. Default tests verify non-increasing vector search scores, block metadata round-tripping, manifest snapshots, temporal graph snapshot restore, and block-chain snapshot lookup. Disabled WDBX builds preserve the same manifest shape where possible and add `"disabled":true`; key-value/vector/search/block/spatial/temporal write paths return feature-disabled errors instead of fabricating successful persistence.

This contract does not prove distributed sharding, AES-256 encryption, RBAC, Swift/Python/TensorFlow implementations, Kubernetes/H100 deployments, regulatory certifications, production QPS/latency/accuracy, energy-use, or comparative model-benchmark claims. Keep those out of public collateral unless they are backed by new executable tests, benchmark artifacts, or implementation files.

## AI identity and multi-persona surface

`abi_ai::identity` (`crates/abi-ai/src/identity.rs`) is the executable
mirror of the Abbey Core Identity contract:

- Abbey is the only `primary_user_facing` profile; Aviva is the direct expert
  mode; ABI is the orchestration/governance profile.
- Default routing prior is Abbey-primary (`DEFAULT_ABBEY_WEIGHT` /
  `DEFAULT_AVIVA_WEIGHT` / `DEFAULT_ABI_WEIGHT`); keyword evidence may still
  select Aviva or ABI.
- `primary_declaration` is product direction, not proof that every named
  capability is Current.
- `capability_claims` map areas such as visual generation, distributed AI, and
  empirical benchmarks to Current / Partial / Proposed with explicit boundaries.

Human-readable companion: `docs/spec/abbey-core-identity.mdx`. Local profile
responses remain deterministic templates via `crates/abi-ai/src/incremental.rs` /
`crates/abi-ai/src/router.rs` — not live model quality or distributed multi-host claims.

## AI/WDBX completion contract

Completion persistence is opt-in. Completion helpers must not mutate WDBX when storage is not requested, when input is invalid, or when WDBX is disabled.

When WDBX is enabled and storage is requested, completion paths may store JSON completion metadata, record query/response vectors, and append a conversation block linked to the previous block. Result fields expose persisted IDs when storage succeeds; they remain unset when persistence is skipped or unavailable. Metadata includes kind, model, profile, audit fields, weighted constitutional escore, byte counts, and query/response vector IDs. WDBX exposes public chain-integrity verification across real and disabled builds (`crates/abi-wdbx/src/mvcc.rs`).

AI scheduler integration is exposed through scheduler-backed completion/training/agent helpers in `abi-ai` / `abi-core`. Real AI builds submit scheduler tasks that fill caller-owned context results and attach any scheduler memory tracker to WDBX-backed work. Disabled AI builds preserve public declarations with feature-disabled or degraded local no-op paths.

## CLI command contract

The CLI command surface is guarded by golden fixtures under `tests/golden/` and the frozen command array in `crates/abi-cli/src/usage.rs`:

- `help`
- `complete`
- `train`
- `agent`
- `backends`
- `plugin`
- `auth`
- `twilio`
- `tui`
- `dashboard`
- `wdbx`
- `scheduler`
- `nn`

The top-level `abi --tui` shortcut is handled in `crates/abi-cli` outside the frozen `usage.commands` array. `abi complete` prints completion governance/persistence observability (`audit_passed=`, `audit_escore=`, `audit_vetoed=`, `persisted=`, WDBX counts, vector IDs, metadata key, and block hash when available) for its transient in-memory WDBX store. `abi agent plan <input>`, `train <abbey|aviva|abi|all>`, `multi <input>`, and `spawn [--background] [--workers <spec>] <input>` run through local scheduler-backed AI helpers; they do not imply live external model training or distributed agents. `abi agent browser [--url <url>] [--execute --confirm] <task>` emits a reviewed local orchestration plan and local planner result. It does not embed or launch a browser; real navigation remains an external MCP integration step. `abi agent tui` uses a bounded raw-mode editor when both stdin and stdout are TTYs; redirected input preserves the deterministic legacy line mode and bytes. `abi dashboard` / `abi tui` enter a raw-mode refresh loop on a TTY; `--once`, `--json`, or non-TTY force one-shot digest (`crates/abi-cli/src/dashboard.rs`). `abi scheduler status` reports a one-shot CLI scheduler probe with task counts and attached memory-tracker counters; it is not a long-running daemon.

`abi nn` is a miniature character-level demo trainer behind the nn feature: `nn train "<text>"`, `nn train --jsonl <path> [--field <name>]`, and `nn sample ...`. It is not a production LLM trainer, distributed trainer, or external model benchmark surface.

`abi wdbx <db|block|query|benchmark|simulate|cluster|compute|secure|gpu|api>` is a WDBX runtime control surface backed by the versioned store (`crates/abi-cli/src/wdbx/`). New stores use v2; the v1 segment/JSONL/WAL engine remains the compatibility reader and verified migration oracle. `db compact <path> [--codec none|pq|autoencoder]` publishes a verified immutable v2 generation: `none` preserves vector bits exactly, while `pq` and `autoencoder` are explicit lossy policies that report artifact and quality evidence. `cluster local-demo` proves exact authenticated 3-9 process behavior on one host, not production multi-host deployment. `compute info` reports separate compiled/available/initialized/executed/runtime-verified states, performs a bounded remote DOT probe only when explicitly configured, and preserves deterministic CPU fallback. `secure` keeps the existing reference demos while exposing separately named educational DGHV refresh and optional pinned TFHE-rs paths. These surfaces do **not** establish production sharding, ANE residency, CUDA/Vulkan runtime execution, production/SOTA learned compression, an independent cryptographic audit, or production-secure FHE — see `docs/spec/wdbx-north-star.mdx` and `docs/contracts/external-claims-audit.mdx`.

## MCP contract

The MCP server exposes JSON-RPC 2.0 over stdio plus a custom loopback HTTP compatibility endpoint. `GET /sse` returns one endpoint-discovery event and closes; `POST /message` handles one JSON-RPC message per connection and returns request responses directly over HTTP. This is not a conforming persistent MCP HTTP+SSE channel, and no such claim is made. Feature-backed tools must expose explicit degraded responses when AI or WDBX is disabled; for example, `ai_train` reports training disabled when the AI stub returns `accepted=false`, and `ai_complete` rejects empty input before touching WDBX. Request bodies are capped at 64 KB (`protocol.MAX_REQUEST_SIZE`) and must start with a JSON object; both stdio and HTTP inherit a shared nesting bound (`protocol.MAX_JSON_DEPTH`, currently 32) that rejects over-nested `{`/`[` containers before JSON parse (TM-008). MCP completion, training, query, and stats tools resolve and open WDBX per call rather than claiming a shared long-lived writer; per-call output reports governance fields, call deltas, and total WDBX counts where applicable. When WDBX is enabled, `wdbx_query` seeds local Abbey/Aviva/Abi profile vectors, uses the persisted temporal/causal graph, and returns a hybrid-ranked local match with semantic, temporal, causal, and persona component scores plus `ranking=hybrid`.

`ai_train` dataset and artifact paths are confined under the training data root: process cwd by default, or `ABI_TRAIN_DATA_ROOT` when set. Middleware still rejects `..` segments on all `file_path` fields; the training path additionally rejects absolute paths outside the root and realpath/symlink escapes. This is local path sandboxing, not a full multi-tenant chroot.

Contract tools are:

- `ai_run`
- `ai_complete`
- `ai_learn`
- `ai_train`
- `wdbx_query`
- `scheduler_stats`
- `scheduler_info` (compatibility alias for scheduler stats)
- `connector_test`
- `gpu_status`
- `plugin_list`
- `wdbx_stats`
- `plugin_run`

`connector_test` uses deterministic local connector paths only; it does not perform live network dispatch. `plugin_list` loads the bundled plugin manifests through `PluginManager` and returns their metadata, while `plugin_run` executes the bundled plugin `run()` implementations.

HTTP defaults to `127.0.0.1:8080`; use `ABI_MCP_HTTP_PORT` to select another loopback port. Empty, invalid, zero, or out-of-range overrides fall back to `8080`; HTTP bind failure is non-fatal and leaves stdio running. Set `ABI_MCP_HTTP_TOKEN` to require `Authorization: Bearer <token>` on the custom loopback HTTP transport. Native clients normally omit `Origin`; a present browser-style origin is accepted only for exact `localhost` or `127.0.0.1` origins and otherwise rejected before authentication or dispatch. Accepted notifications receive `202 Accepted` with an empty body. Stdio JSON-RPC remains tokenless local IPC.

The WDBX REST API (`abi wdbx api serve [port]`) binds `127.0.0.1` and exposes `POST /insert`, `POST /query`, `POST /verify`, `GET /health`, and `GET /stats`. Set `ABI_WDBX_REST_TOKEN` to require `Authorization: Bearer <token>` on the HTTP transport. This is loopback/local hardening only; non-loopback exposure still requires a reviewed fronting layer with TLS, authorization, rate limiting, and deployment controls.

## Plugin registry contract

Plugin discovery is static from `crates/abi-plugins/plugins/*/abi-plugin.json`. Bundled plugin directories validated by `crates/abi-foundation/src/plugin_manifest.rs` include `mod.rs`, `stub.rs`, and `abi-plugin.json`.

Required manifest fields:

- `name`
- `version`
- `description`
- `target_feature`
- `entry_point` (safe relative `.rs` path; no absolute paths, traversal, empty/`.`/`..` segments, Windows drive separators, or backslashes; the file must exist under the plugin directory)

`targetFeature` and `entryPoint` manifest aliases are accepted by the generator and plugin manager. `crates/abi-core/src/registry.rs` stores plugins as `PluginDescriptor` values containing manifest metadata and exposes stable accessors such as `plugin()`, `plugins()`, and related list/format helpers. `abi plugin list` includes plugin count, version, target feature, entry point, and description. Legacy register helpers remain supported where present for compatibility.

Golden / unit coverage verifies generated metadata for the bundled example plugins, including the WDBX-targeted fixture.

## Connector contract

Connectors provide deterministic local behavior and explicit live-transport boundaries (`crates/abi-connectors`).

Discord connector calls validate:

- non-empty printable ASCII credentials without whitespace
- numeric snowflake-like client/channel/author IDs
- non-empty message content no larger than 2000 bytes
- local send/receive logs include IDs and content byte counts, not message text

Twilio connector calls validate:

- account SIDs shaped as `AC` plus 32 hex characters
- auth tokens shaped as 32 hex characters
- non-empty base URL and non-zero timeout
- ConversationRelay aliases (`event`, `callSid`, `from`, camelCase memory/intelligence fields) and wrong-typed payload rejection before building local responses or live TwiML/form payloads
- XML escaping for TwiML `<Say>` and `<Redirect>` text and URL-encoded form fields
- live response logs include HTTP status and body byte counts, not provider response bodies

OpenAI and Anthropic connectors validate shared connector config and keep local streaming responses deterministic. Live HTTP dispatch remains an explicit live transport path, and connector tests validate malformed live-path inputs before network dispatch. Live URL construction (`crates/abi-connectors/src/url.rs` `join_url`) requires a `https://` base URL scheme (`require_https_base_url`); cleartext `http://` and other schemes return `InsecureBaseUrl`. Local/mock connectors never call `join_url`. This is scheme enforcement only — not host allowlisting, certificate pinning, or mTLS.

## Credential storage contract

`abi auth` persists provider credentials as local plaintext JSON by default (resolved from `ABI_CREDENTIALS_PATH`, `XDG_CONFIG_HOME/abi/`, or `~/.abi/` as fallback). On POSIX-capable targets, the credential directory is created or repaired as owner-only (`0700`) and the credential file is opened/truncated with owner-only permissions (`0600`) before secret bytes are written; existing permissive files are tightened before overwrite. On Windows targets, an owner-only DACL is applied via SDDL after write, and WDBX private-key reads now fail closed unless the existing file has that exact protected owner-only DACL. Both Windows paths are cross-compiled with warning-denied Clippy; **runtime** verification still requires a Windows host. Opt-in macOS login keychain storage is available via `ABI_CREDENTIALS_BACKEND=keychain` (`crates/abi-foundation/src/credentials/keychain.rs`, Security.framework `SecItem*` — OS-provided at-rest protection only; not hardware-backed, not audited; runtime-verified on macOS host only). The separately reported, additive `LinuxSecretServiceProvider` uses the maintained `secret-service` Rust API over an encrypted in-process D-Bus session, stores only the fixed ABI credential fields under bounded source-controlled attributes, redacts upstream error detail, and zeroizes loaded temporary secret bytes. Linux source and tests cross-compile, but no Linux Secret Service daemon round trip has run; `runtime_verified` changes only after an actual provider operation succeeds. This explicit provider does not change `abi auth` backend selection: off-macOS `keychain` requests still fall back to the file store with a disclosed status label, and Windows Credential Manager remains unimplemented. On POSIX TTYs, `auth signin` disables terminal echo while reading secrets and restores it afterward; Windows echo-suppress remains a disclosed gap. This is local credential hardening plus a compile-checked Linux provider, not encryption, RBAC, or a regulatory-compliance claim.

Ambient WDBX v2 generation directories (resolved via `ABI_WDBX_PATH` / XDG / `~/.abi/wdbx`) are created or repaired as owner-only (`0700`) on Unix when opened through `VersionedStore`; private encryption/signing key files are separately required to be owner-only. This is directory permission hardening only, not encryption, RBAC, or production multi-host integrity. Legacy v1 WAL frames remain CRC32-framed rather than keyed-MACs.

## Validation gates

For source changes:

```bash
./tools/check.sh
```

Thin compatibility entrypoint: `./build.sh check` → `./tools/check.sh`.

For public feature/plugin API changes, rely on compile-time `Plugin` trait + `assert_plugin_parity!` in `abi-plugins` and the workspace test/golden suite under `./tools/check.sh`.
